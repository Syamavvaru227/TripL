# Deploying TripL

TripL ships as **one Docker container**: the React app is built during the image
build and FastAPI serves both the SPA and the `/api` routes from the same origin.
One container means one public URL, no CORS juggling, and no API base URL to
configure on the frontend.

```
Browser ──► https://<service>.onrender.com
                    │
              FastAPI (uvicorn, $PORT)
                    ├── /            → built React SPA
                    ├── /assets/*    → JS/CSS/images
                    └── /api/*       → JSON API
                              │
                    MySQL (external, managed)
                              │
              Wikipedia · Nominatim · OpenStreetMap · OSRM (no keys needed)
```

Host: **Render**, using the `render.yaml` blueprint in the repo root.
Database: **managed MySQL** (Aiven free or TiDB Cloud Serverless free).

---

## 1. Create the MySQL database

The app reads a single `DATABASE_URL`. It defaults to SQLite when unset — which
works, but Render's free tier has an **ephemeral disk**, so every redeploy and
spin-down wipes registered accounts and saved itineraries. Use a real database.

1. Sign up for a free MySQL:
   - **Aiven** — free 1 GB MySQL service, or
   - **TiDB Cloud Serverless** — free 5 GB, MySQL-compatible.
2. Create the service and copy the connection details: host, port, user,
   password, database name.
3. Build the URL:

   ```
   mysql+pymysql://USER:PASSWORD@HOST:PORT/DBNAME
   ```

   **URL-encode the password.** A literal `@`, `#`, `/` or `:` will break the URL:

   | Character | Encoded |
   |-----------|---------|
   | `@` | `%40` |
   | `#` | `%23` |
   | `/` | `%2F` |
   | `:` | `%3A` |

4. **If the connection fails with an SSL/certificate error**, the provider
   requires TLS. Both Aiven and TiDB require it by default. Fix:

   ```bash
   # Download the provider's CA certificate
   mkdir -p tripl-backend/certs
   # save it as tripl-backend/certs/ca.pem
   ```

   Then append the CA path to the URL (the container's working directory is
   `/app`, and `tripl-backend/` is copied there, so this path is correct):

   ```
   mysql+pymysql://USER:PASSWORD@HOST:PORT/DBNAME?ssl_ca=/app/certs/ca.pem
   ```

   A CA certificate is public information — committing it is safe.

## 2. Deploy on Render

1. [dashboard.render.com](https://dashboard.render.com) → **New** → **Blueprint**.
2. Connect the repo `github.com/Syamavvaru227/TripL`. Render reads `render.yaml`
   and shows one web service, `tripl`.
3. Render prompts for the env vars marked `sync: false`. Paste `DATABASE_URL`
   from step 1.
4. Confirm `JWT_SECRET_KEY` shows as generated (it must be stable — if it changes
   between boots, every existing login is invalidated).
5. Click **Apply**. First build takes ~4–6 minutes (npm install + pip install).

If the service name `tripl` is already taken on Render, your URL becomes
something else — update `APP_BASE_URL` and `CORS_ORIGINS` in the Render dashboard
to match. Those only affect links inside emails.

## 3. Environment variables

Set on the Render service (blueprint sets most of these automatically):

| Key | Required | Notes |
|-----|----------|-------|
| `DATABASE_URL` | **Yes** | `mysql+pymysql://…` as built above |
| `JWT_SECRET_KEY` | **Yes** | Auto-generated by the blueprint; keep it stable |
| `APP_ENV` | Yes | `production` |
| `PORT` | Auto | Render injects it (default `10000`); the container binds it |
| `APP_BASE_URL` | Recommended | Public URL, used for links in welcome emails |
| `CORS_ORIGINS` | Optional | Not needed for the single-service deploy (same origin) |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Optional | Blueprint sets `1440` so logins last a day |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_USERNAME` / `SMTP_PASSWORD` / `SMTP_FROM_EMAIL` | Optional | Without these, the welcome email is skipped silently |
| `ORS_API_KEY` | Optional | Routing falls back to the public OSRM service |

Do not set `VITE_API_URL` in production. Empty means "same origin", which is
correct here. It exists only for deployments where the frontend is hosted
separately from the backend.

## 4. Verify the deploy

Run these against your real URL. All six should pass:

```bash
# 1. Health check (this is also Render's health check path)
curl -s https://<service>.onrender.com/api/health
#    → {"status":"ok"}

# 2. SPA is served
curl -s -o /dev/null -w "%{http_code}\n" https://<service>.onrender.com/
#    → 200

# 3. Client-side route falls back to index.html
curl -s -o /dev/null -w "%{http_code}\n" https://<service>.onrender.com/explore
#    → 200

# 4. Live place discovery
curl -s "https://<service>.onrender.com/api/places/nearby?city=Guntur" | head -c 200

# 5. Wikipedia history (the endpoint the destination page calls)
curl -s "https://<service>.onrender.com/api/places/wiki-history?name=Jinnah%20Tower" | head -c 200
```

Then in the browser, walk the full flow:

1. Open the site → the landing hero renders with its styling.
2. **Explore** → search `Guntur` → real places appear on the map and as cards.
3. Open a destination → **the Know India tab loads history.** This is the specific
   proof that the API base URL is same-origin and not pointing at `localhost`.
4. **Plan Journey** → run the 5-step wizard → an itinerary is generated.
5. Register a phone account → log out → log back in.
6. **Force a redeploy, then log in again.** The account surviving is the proof
   that MySQL is wired and the app is not silently on SQLite.

## 5. Free-tier behaviour to expect

- **Sleep after 15 idle minutes** (~60 s cold start on the next request).
  For a demo, ping `/api/health` every 10 minutes with a free uptime monitor
  (UptimeRobot, cron-job.org) to keep it warm.
- **The first place query is slow** — 13–22 s while it fetches live data from
  Wikipedia/OSM. Every later query for that city is ~1 s from cache. Click
  through your demo city once *before* recording or presenting.
- **Ephemeral disk.** Without an external `DATABASE_URL`, data resets on every
  spin-down and redeploy.

## 6. Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| Build fails at `COPY --from=frontend` | Vite wrote its output somewhere unexpected | The Dockerfile overrides `outDir` to `dist/`; check the build log for the path it names |
| Build fails on Node version | Vite 8 needs Node ≥ 20.19 / 22.12 | Bump the `FROM node:` tag in the Dockerfile |
| Deploy fails the health check | `initialize_database()` raises at startup when the DB is unreachable, so the app never binds the port | Open the Render log; it is almost always a wrong `DATABASE_URL` or an unencoded password character |
| `Access denied for user` | Password has an unencoded special character | URL-encode it (step 1.3) |
| `SSL connection is required` | Provider mandates TLS | Add `?ssl_ca=/app/certs/ca.pem` (step 1.4) |
| 404 on every route | Nothing is listening on the port Render routes to | The CMD binds `${PORT:-8000}`; confirm `PORT` is not overridden in the dashboard |
| Logged-in users get 401 after a restart | `JWT_SECRET_KEY` changed | Set it once and leave it alone |
| Welcome email never arrives | SMTP vars unset | Fill in the `SMTP_*` values |

## 7. Deploying somewhere else

The Dockerfile is host-agnostic. Any platform that builds a Dockerfile and
injects `PORT` works: Railway, Fly.io, Koyeb, a VPS, or Hugging Face Spaces.
Only `render.yaml` is Render-specific.

```bash
# Build and run the exact production image locally
docker build -t tripl .
docker run -p 8000:8000 -e DATABASE_URL="..." -e JWT_SECRET_KEY="..." tripl
# → http://localhost:8000
```

## 8. The uncommitted-artifact rule

Render builds from GitHub, so **nothing deploys until it is committed and
pushed**. Locally, `tripl-backend/.env` and `tripl-frontend/.env` hold real
secrets and are gitignored — never commit them. `.dockerignore` also keeps them
out of any locally built image. Only the `.env.example` templates are tracked.
